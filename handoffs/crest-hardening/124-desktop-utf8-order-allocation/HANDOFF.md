# 124 — Desktop position allocator can write invalid UTF-8

Status: owner source fix integrated in `20467e5`; C++ compilation, regression,
sync capture, opposite-platform replay and installed R1 acceptance pending
Owner: desktop/sidebar plus sync capture
Reviewed source: `ce24827` (R1 core `cfd0127`), 27 September 2026.

## Reproducer and consequence

`SidebarTreeController::ResolveDropDestination` in
`overlay/chromium/src/ahoi/browser/ui/sidebar/sidebar_tree_controller_drop.cc`
selects the visible left/right sibling keys and calls
`GenerateSortKeyBetween` (lines 163–181). The latter compares byte strings,
then returns a one-byte midpoint at lines 291–295.

Two valid opaque UTF-8 keys can therefore produce an invalid key:

| Left | Right | First differing bytes | Generated byte |
| --- | --- | --- | --- |
| `é` (`c3 a9`) | `€` (`e2 82 ac`) | `c3 < e2` | `d2` |

`d2` alone is an incomplete UTF-8 leading byte. It sorts between the bounds
as bytes, but cannot be decoded as a Unicode string. The same allocator is used
by normal sidebar drop and multi-page move, and append paths can grow an
already long key without a preflight bound. `TabTreeStore::MoveNode` checks only
for a nonempty key; `ValidateNode` also checks only nonempty and does not check
UTF-8. Thus a local write can retain a key that the shared wire/Swift opaque
string representation cannot round-trip byte-for-byte. Exact downstream
failure or repair behavior needs an actual capture/replay test; this review
does not claim it was executed.

This is distinct from 120's byte-exact comparison fix and from cfd0127's
projection tests, whose C++ explicit move uses a hand-authored `+ "@"` key in
`sync_workspace_merge_unittest.cc`, bypassing the production allocator.

## Required owner change and evidence

Use only a valid UTF-8 key strictly between the observed byte bounds. For the
example, appending an ASCII byte to the valid left key is one possible result
because the first differing byte already orders it below the right key. Keep
the current explicit no-space refusal when a valid bounded key is unavailable.
Check size and serialization requirements before calling `MoveNode` or
`CreateNode`, including near-limit append and projected-marker tails. Do not
silently rewrite untouched siblings, field clocks or raw Page bytes during
passive projection.

Exercise the real `ResolveDropDestination`/`GenerateSortKeyBetween` path with
Unicode bounds, a prefix pair, equal-key/ID tie, and a near-limit key. Verify
the actual returned key is strict between bounds by unsigned UTF-8 bytes,
remains valid UTF-8, survives `TabTreeStore` persistence/reopen, sync capture
and opposite-platform decode/replay, and stamps only the explicitly moved
location. Include an actual projected late root and a native Page moved after
it from 118. The stored key, not a hand-authored equivalent, must feed the
opposite platform. Preserve refusal as a clean no-mutation outcome if an
interval is exhausted. C++ native/installed evidence remains owner-gated.

this finding. H3/H5 resource leases remain separate.
